# 流量包采用不同币种定价时，怎样保存汇率日期与实际支付差异？

<EvidenceBadge type="standard-rule" label="服务限制核查" />
<EvidenceBadge type="client-kernel" label="性能约束分析" />

## 一、核心答案与适用前提

针对“**流量包采用不同币种定价时，怎样保存汇率日期与实际支付差异？**”，按量方案的核心权衡法则：**没有免费的灵活性。由于按量用户不贡献稳定的每月现金流，服务商通常会在‘并发设备数、峰值带宽、专线节点池开放度与提单支持优先级’四个维度施加工程限制，以防止按量用户占用过多宝贵的商业核心资源。**

常见的四项服务约束机制：
1. **严格的并发连接数限制 (Device/IP Limit)**：月付套餐通常允许 3~5 台设备同时在线，而按量方案常被严格限制为 1~2 台设备，多端同时连接会触发鉴权 403 熔断。
2. **峰值带宽 (Speed Cap) 梯级受限**：部分服务商将月付用户开放至 1000Mbps，而按量套餐在 QOS 策略上被限速至 50Mbps~100Mbps。
3. **专线节点池隔离**：最优质的 0 丢包 IPLC 专线可能仅向月付/年付用户开放，按量用户仅能使用标准公网中继或直连节点。
4. **小额出金与工单手续费**：若需要退款或申请人工客服介入，按量方案往往需要扣除固定手续费或面临更长的排队工单响应时间。

## 四、核心推导步骤与典型算例

### 算例：家庭双端共用受限按量方案的冲突推演
某用户购买了一款性价比极高的 $200.0\text{ GB}$ 不限时按量包，用于家庭备用。
- 官方未在显眼处说明，但后台底层配置了：**`max_devices: 1`（仅限单一客户端同时发起连接）**；
- **场景触发**：
  - 傍晚 19:30，客厅 Apple TV 开启代理准备观看海外流媒体；
  - 19:35，书房电脑开启客户端准备提交一份海外紧急代码。

**冲突机制与事故推导**：
1. **计费鉴权网关响应**：
   - Apple TV 建立的长连接持有 Session Token A；
   - 电脑发起连接时，网关检测到并发 IP 数 $> 1$，判定为违背并发条款；
   - 网关策略一（踢出前置）：强制将 Apple TV 的 Session A 断开，Apple TV 画面瞬间转圈卡死报错；
   - 网关策略二（拒绝后置）：直接给电脑端下发 TCP RST，电脑端 Git 报错 `Connection reset by peer`。
2. **业务代价核算**：
   用户虽然节省了套餐月费，但在关键时刻因单并发限制导致家庭娱乐与核心生产力发生严重冲突。
3. **对账治理**：
   若需多端共用，必须在选型阶段将“并发设备数 $\ge 2$”作为死指标，在主站筛选支持多连接的按量方案，或在本地配置主路由集中翻转。

## 五、底层网络机制与边界案例

### 1. TC（Traffic Control）与令牌桶限速机制
服务商在 Linux 节点上通常使用 `tc` 配合 HTB（Hierarchical Token Bucket）对按量用户配置独立的 QOS 规则集。当按量用户的下载速率瞬间冲高至限制阈值时，网关直接暴力丢弃后续数据包。若客户端使用的是传统 Cubic 拥塞控制，会引发剧烈的拥塞窗口收缩，导致实际下载速度发生断崖式下跌。

### 2. 动态 IP 与单 IP 限制的冲突
很多移动宽带采用 CGNAT（运营商级大局域网），用户的公网出口 IP 可能会在数分钟内发生跳变。若服务商的“单设备限制”是粗暴根据访问出口 IP 判定，当公网 IP 跳变时，系统会误判为“第二台设备登录”，从而产生虚假的并发封锁。
